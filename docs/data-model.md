# ThinkTwice Data Model

_Status: approved. Last updated: 2026-10-22._

This covers the v1 scope in `docs/mvp.md`. The database is PostgreSQL 18. The tables are created by hand-written SQL migrations in `services/api/migrations/` (the source of truth), and the API queries them through Drizzle ORM.

## Conventions

- **IDs:** UUIDs generated by PostgreSQL (`uuidv7()`, PostgreSQL 18+). They are unguessable and never sequential.
- **Money:** stored as integer **cents** (`amount_cents`), never as floating point. USD only.
- **Dates and times:**
  - Timestamps are `timestamptz`, stored in UTC.
  - The day a purchase happened is a plain `date` (`spent_on`), in the user's local time.
  - Each user has a timezone so "today" and "this month" are correct for them.
- **Naming:** tables are plural `snake_case`; columns are `snake_case`.
- Every table has `created_at` and `updated_at`.

## Tables

### `users`

One row per account. Sign-in itself is handled by Firebase; this links a Firebase account to the app's data.

| Column                     | Type        | Notes                                                       |
| -------------------------- | ----------- | ----------------------------------------------------------- |
| `id`                       | uuid        | Primary key                                                 |
| `firebase_uid`             | text        | Unique, not null. Taken from the verified Firebase ID token |
| `email`                    | text        | Not null. Copied from Firebase for display only             |
| `timezone`                 | text        | Not null, IANA name (e.g. `America/Chicago`)                |
| `monthly_budget_cents`     | integer     | Nullable (budget is optional). Must be > 0 when set         |
| `created_at`, `updated_at` | timestamptz |                                                             |

### `categories`

Each user gets their own copy of the default categories when they sign up, so they can rename, hide or retype them freely.

| Column                     | Type        | Notes                                                       |
| -------------------------- | ----------- | ----------------------------------------------------------- |
| `id`                       | uuid        | Primary key                                                 |
| `user_id`                  | uuid        | Not null, references `users.id`, `ON DELETE CASCADE`        |
| `name`                     | text        | Not null, 1–40 characters                                   |
| `type`                     | enum        | `essential` or `discretionary`                              |
| `is_hidden`                | boolean     | Default `false`. Hidden categories keep their past expenses |
| `sort_order`               | integer     | Display order                                               |
| `created_at`, `updated_at` | timestamptz |                                                             |

- Unique: (`user_id`, lowercase `name`), so no duplicate names per user.
- Unique: (`id`, `user_id`), used by the composite foreign key below.

### `expenses`

| Column                     | Type        | Notes                                                |
| -------------------------- | ----------- | ---------------------------------------------------- |
| `id`                       | uuid        | Primary key                                          |
| `user_id`                  | uuid        | Not null, references `users.id`, `ON DELETE CASCADE` |
| `category_id`              | uuid        | Not null                                             |
| `amount_cents`             | integer     | Not null, > 0, with a sensible upper limit           |
| `spent_on`                 | date        | Not null, defaults to the user's "today"             |
| `note`                     | text        | Nullable, max 200 characters                         |
| `created_at`, `updated_at` | timestamptz |                                                      |

- Foreign key: (`category_id`, `user_id`) references `categories` (`id`, `user_id`). The database itself guarantees that an expense can only use a category belonging to the same user.
- Index: (`user_id`, `spent_on` descending) for the dashboard and forecasts.

## Not stored in v1

- **Forecasts and insights** are calculated on request from the user's expenses, so they are never out of date and there is no extra data to protect.

## Keeping each user's data separate (rule 13)

1. **Identity comes only from the token.** The API verifies the Firebase ID token, looks up `users.id` by `firebase_uid`, and uses that as the only source of "who is asking." User IDs sent by the app are never trusted.
2. **Every query is scoped.** Every read, update and delete on `categories` and `expenses` includes `WHERE user_id = <current user>`. A record that doesn't match returns `404`.
3. **The database enforces ownership too.**
   - Composite foreign keys stop cross-user references.
   - **PostgreSQL row-level security on every table.** For each transaction the API sets the signed-in user's Firebase UID and user ID (`withUserScope` in `services/api/src/db/user-scope.ts`), and the database refuses to return or change any other user's rows even if a query forgets the filter:
     - `users`: only the row whose `firebase_uid` matches the verified token.
     - `categories` and `expenses`: only rows whose `user_id` matches.
     - Outside a user scope, every query sees nothing.
   - Row-level security is **forced**, so it applies even to the table owner.
4. **Database roles follow least privilege.**
   - `thinktwice_owner` owns the tables and runs migrations. It is not a superuser.
   - `thinktwice_app` is what the API connects as. It can only read and write rows (always filtered by row-level security). It can't create, alter or drop tables, change policies, truncate, or switch roles.
   - `services/api/tests/db/` proves all of the above against a real database.
5. **The ML service gets the minimum.** It receives only category type, category name, amount and date for the requesting user. No emails, notes or IDs.
6. **Account deletion is complete.** Deleting the `users` row cascades to all of that user's categories and expenses, and the API also deletes the Firebase account.

## Planned for later versions

- `category_limits`: per-category monthly limits (v1.1).
- `habits`: recurring purchases detected by ML (v1.1).
- Bank connections and imported transactions (Plaid, later). These will need extra protection, such as encrypting access tokens.
